# Audit Policy

## Purpose

Audit records provide a chronological, reviewable account of security-sensitive
and incident-changing activity. They are append-only application records and
must survive normal restarts and account deletion.

## Required fields

Each event records:

- Unique event identifier.
- UTC timestamp generated by the application.
- A truthful actor identity: either an account identifier and its role at the
  time of the event, or the non-account actor `SYSTEM` with no account
  identifier for a trusted automated application operation.
- Action type.
- Target type and identifier.
- Outcome: success or failure when failure auditing is appropriate.
- Relevant before/after values or a concise structured change summary.
- Optional reason or remarks where the operation requires them.

Never record passwords, password hashes, reset secrets, session identifiers,
unnecessary incident content, or an anonymous reporter's display identity.

System actors are reserved for trusted automated application operations such
as one-time first-Administrator bootstrap. They must not stand in for an
authenticated user whose identity is missing. Persist them with a null actor
account identifier and actor role `SYSTEM`; record the affected resource in
the event target. `SYSTEM` is an audit identity only and grants no application
authorization.

## Incident events

- Draft creation and submission.
- Incident creation and edits.
- Withdrawal.
- Claim, assignment, reassignment, and handoff.
- Resolution, including resolution remarks or a safe reference to them.
- Reporter follow-up and reopening, including a safe reference to the required
  explanatory comment without duplicating sensitive comment text in the audit
  record.
- Attachment addition and any authorized removal.
- Anonymous flag at submission without exposing identity.

## Application events

- Registration, self-service password changes, and authentication-relevant events without secret material.
- Responder-promotion request, approval, and rejection.
- Responder-category access changes.
- Account disabling/deletion and password-reset initiation/completion. Reset audit records contain no
  plaintext password, password hash, or reset credential.
- SLO configuration changes.
- Database migration and approved backup restoration.
- AI request acceptance and outcome category, without prompt or response text.

## Integrity rules

- Write the domain state change and its audit event as one logical persistence
  operation. If either cannot be safely persisted, commit neither.
- Do not provide normal update or delete operations for audit entries.
- Preserve audit actor identifiers after account deletion and display a
  tombstoned label rather than erasing history.
- Sort equal-timestamp events deterministically by a monotonic sequence or event
  identifier.
- The application-level log can filter by time, actor, action, and target.
- An incident audit view shows only events for that incident.
- Anonymous incident audit presentation must follow `.agents/anonymity-policy.md`.

Database permissions and append-only application APIs reduce ordinary
modification risk but do not make records tamper-proof against a database or
hosting administrator. Do not claim otherwise.
